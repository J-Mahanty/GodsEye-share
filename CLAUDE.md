# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GodsEye — city-wide ANPR (Automatic Number Plate Recognition) intelligence platform. A plate reader tuned for degraded real-world captures, a spatial-temporal trajectory engine over a GIS camera network, macro traffic analytics, and a real-time alert queue, all built on one SQLite database. Built for SIH 2026 (Team Prometheus). Full technical writeup, measured accuracy tables, and the reasoning behind every design decision live in `README.md` — read it before making changes to `anpr/` or `core/`, since the numbers there are load-bearing (the dashboard renders `models/benchmark.json`, the same file the README quotes).

## Commands

```bash
pip install -r requirements.txt

python seed.py                                  # backfill ~6h of simulated city traffic into SQLite (~65s)
uvicorn api.main:app --reload --port 8000        # API + live feed  → http://localhost:8000/docs
streamlit run dashboard/app.py                   # control room     → http://localhost:8501

python tests.py                                  # end-to-end self-check (58 checks) — run before any demo/PR
python -m anpr.benchmark --samples 100 --scenes 60 --layouts 100 --burst 5 --json models/benchmark.json
python -m anpr.compare_backends --samples 100    # classical/CRNN/EasyOCR/anpr_ocr on synthetic captures
python -m anpr.compare_backends --real --seeds 8 # same, on real photos, swept across 8 vehicle-split seeds
python -m anpr.camera_sheet                      # render every camera scenario side by side, for visual inspection
python -m core.repair --hours 6                  # run the repair pass over recent history (also POST /api/repair/run)
```

- `python tests.py` is the only test suite (no pytest) — it points `config.DB_PATH` at a scratch temp file so it never touches `data/godseye.db`, then walks reading → sightings → trajectory → analytics → every alert rule in one process. There is no way to run a single check in isolation; read `tests.py` and search for the `check(...)` name if you need to isolate one.
- Both shipped models (`models/*.joblib`, CRNN weights) are committed, so nothing needs training to run the platform. If `models/` is emptied: `python -m anpr.train_crnn` retrains the CRNN (CPU, tens of minutes, resumable); the classical glyph classifier retrains itself on first use (~3 min).
- `torch` is an optional dependency (`extra == "neural"` in `requirements.txt`). Without it, `anpr/ocr.py` falls back to the classical segment-and-classify engine automatically — don't assume torch is present when touching shared OCR code paths.
- The dashboard reads the database directly and works with the API stopped; the API process is what runs the live simulated camera feed and incident injectors.
- `GODSEYE_DB` env var overrides the SQLite path; `GODSEYE_BURST=1` forces single-frame reads instead of the default 5-frame burst (`config.BURST_FRAMES`).

## Architecture

Everything hangs off one primitive: a `sightings` row (plate, camera, timestamp, confidence). Nothing upstream of `core/db.py` knows whether a sighting came from the simulator or a real camera — swapping in real hardware means writing rows into `sightings`, nothing else changes.

```
sim/city.py (simulated vehicles)
  → anpr/plates.py (plate synthesis, faults) → anpr/camera.py (8-stage physical camera model)
  → anpr/ocr.py (localise → unwrap → CRNN or classical → burst-fuse)  [the engine]
  → core/db.py (sightings / inferences / alerts / watchlist)
  → core/trajectory.py, core/analytics.py, core/alerts.py, core/clones.py, core/repair.py
  → api/ (FastAPI + WebSocket)  → dashboard/app.py (Streamlit, deck.gl maps)
```

**`anpr/` — the reader.** `ocr.py` is the engine entrypoint (`ANPREngine.read()` for a tight crop, `read_frame()` for a whole photo via `detect_plate_candidates()`). It tries every plausible one-row/two-row layout through the CRNN in one batch and lets the exact CTC score pick the winner — segmentation is never committed to before recognition, and that's the central design decision the whole reader is built around (see README §1 for why). `crnn.py` has the CRNN + CTC decode + the exact forward-backward confidence score (`ctc_score`, checked against `torch.nn.CTCLoss` to 1e-4 — do not replace it with a heuristic confidence measure, an earlier one scored AUROC 0.367, worse than chance). `segment.py`/`model.py` are the classical fallback path (used only without torch or trained weights). `camera.py` is the physical capture model — 8 ordered stages (surface → geometry → atmosphere → illumination → optics → sensor → JPEG → crop/zoom); the ordering is physically motivated and documented in `AUGMENTATION.md`, don't reorder stages without reading it. `benchmark.py` / `compare_backends.py` produce the committed JSON that README tables and the dashboard both render from — regenerate rather than hand-edit those JSON files.

`detect_plate_candidates()` (`anpr/ocr.py`, near line 535) auto-loads `models/yolov8n-obb-plate.pt` via `_load_yolo()` if the file exists, routing through the trained YOLOv8-OBB detector; it silently falls back to the classical morphological localiser (`_detect_plate_candidates_classical`) if the weights file is absent or `ultralytics` isn't installed. `_load_yolo()` resolves its checkpoint off `config.MODEL_DIR` like the rest of the codebase (it used to be a bare relative string, which silently fell back to the classical localiser whenever the cwd wasn't the repo root).

**Only the `benchmark.py` "whole frames" sub-test and `read_frame()` callers exercise the YOLO detector at all.** The much more commonly quoted per-condition/burst/OVERALL numbers in `anpr.benchmark`'s output feed `ANPREngine.read()` a pre-made plate crop directly and never call `detect_plate_candidates()` — swapping the detector changes nothing in those numbers, only in the `scenes`/`whole frames` line. Don't infer detector quality from the headline benchmark numbers.

**`core/` — everything downstream of a stored sighting.**
- `trajectory.py` — confusion-aware search (`0↔O`, `8↔B`, etc. cost less than a plain edit) and route reconstruction over the camera graph (`network.py`).
- `analytics.py` — density/flows/O-D/bottlenecks/heatmap, all derived from consecutive-sighting pairs; speed is only computed between *adjacent* cameras in the graph.
- `alerts.py` — ingest-time rules (watchlist, clone, loitering, detour, speeding, odd_hour), rate-limited/de-duplicated per plate per rule within a rolling window.
- `clones.py` — query-time clone verdict, separate from the ingest-time alert rule. Screens out misreads (OCR-confusable plate plausibly at that camera), weak reads (<`CLONE_MIN_CONFIDENCE`), and near-camera geometry noise before asserting a clone, because at this engine's accuracy a misread and a real clone produce the same signature. Only `confident` verdicts (multiple independent conflicts) reach the alert queue.
- `repair.py` — recovers refused (below-floor) captures by matching their retained CTC lattice against what neighbouring cameras saw. Writes to `inferences`, never to `sightings` — this distinction is load-bearing: candidate sets for repair are built only from real `sightings`, so a repaired guess can never become evidence for another repair.

**`config.py`** is the single source of truth for paths and tunables (confidence floor, burst size, alert thresholds, clone thresholds) — resolved relative to the file itself so it doesn't matter what directory uvicorn/streamlit is launched from.

**`api/`** is a thin FastAPI layer over `core/` and `anpr/` — routes in `api/routes.py`, shared state/simulator wiring in `api/state.py`. See README's API table for the endpoint list.

**`dashboard/`** — Streamlit control room. The live map is an `st.fragment` with `run_every` (not a sleep-based rerun loop — that was a real bug: Streamlit reruns the whole script on a naive rerun, rebuilding every map and leaking WebGL contexts). `pdk.types.String` must wrap any bare string passed to a pydeck layer property (e.g. `width_units`) — an unwrapped string gets compiled into a data accessor by pydeck and silently breaks rendering. Both are documented with the measurements that found them in README §3.

**`data/cameras.json`** — 35 real Kolkata junction coordinates + 52 road links with shape points; this is what the map, trajectory reconstruction, and analytics all route against.

## In-progress / untracked work: real-photo accuracy

The shipped models are trained/benchmarked entirely on synthetic data (`anpr/plates.py` + `anpr/camera.py`'s render pipeline). Untracked work this repo currently carries is an attempt to move both stages onto real photos — read the following before repeating any of it:

**YOLOv8-OBB plate detector — done, works.** `train_yolo.py` fine-tunes `models/yolov8n-obb-plate.pt` (loaded automatically by `anpr/ocr.py`, see above) from real photos. Real training data: `convert_bbox_to_obb.py` converts a Roboflow YOLOv8-detect export (axis-aligned bbox labels) to the OBB label format the model needs; `convert_kaggle_to_obb.py` does the same from Pascal-VOC XML. `train_yolo.py` always fine-tunes from whatever checkpoint is already at `models/yolov8n-obb-plate.pt` rather than the stock base weights, and reads `results.save_dir` for where to copy `best.pt` from — **never hardcode that path**, ultralytics silently auto-suffixes the run directory (`yolov8n-obb-plate-model-2`, `-3`, ...) whenever a previous run's directory already exists, and copying from a stale hardcoded path silently installs the wrong checkpoint (this happened once; `models/yolov8n-obb-plate.pt.run1.bak` is the recovered original). Measured: the detector finds a candidate plate region in 100% of real photos tried; `yolo obb val`/`yolo obb predict` need `device=mps` passed explicitly on Apple Silicon or they silently run on CPU. Any mAP number from `dataset_v1_obb`/`dataset_indian_obb` is inflated — Roboflow's random image-level train/valid/test split does not separate video sequences, so nearly-identical frames of the same vehicle crossing leak across splits.

**CRNN reader on real photos — tried, does not work, and 540 more images won't fix it.** `finetune_crnn_real.py` and `finetune_crnn_real_v2.py` fine-tune `models/crnn.pt` on real labelled plate crops, writing to a separate checkpoint (never overwrites `models/crnn.pt`). `build_real_crnn_dataset.py` assembles the largest available real training set (540 crops / 83 unique vehicles, from `indian-number-plates-dataset`'s XML text labels, `dataset_v1_bbox` filenames that embed the plate, and manually-transcribed video-frame clusters in `cluster_manifest.json`/`real_plate_transcriptions.json`), split by vehicle identity so validation never sees a frame of a training vehicle. Result: **0% exact-match on held-out real vehicles**, both with 25 and with 540 real examples — the CRNN's convolutional features were learned entirely from the synthetic camera model's rendering artifacts and don't transfer to real JPEG/lens/sensor statistics; more epochs on this scale of real data measurably improves output *plausibility* (state-code and plate-shape prior) but not per-character accuracy. Training from scratch on real data alone is worse, not better: the current 540-crop set is missing 4 of 36 alphabet characters (I/O/V/Z) entirely, so a from-scratch model provably could never learn them. Rough estimate to get a real fine-tune into the 85%+ range: **low thousands of distinct labelled real plates** (not frames — redundant frames of the same vehicle don't add character diversity), spread across varied real conditions, not the ~90 vehicles available in-repo today.

**EasyOCR and anpr_ocr — evaluation-only third/fourth recognisers, opt-in, never the default.** `anpr/easyocr_reader.py` and `anpr/anpr_ocr_reader.py` mirror `crnn.py`'s `available()`/`load()` shape and plug into `ANPREngine` via `easyocr_reader=`/`anpr_ocr_reader=` constructor params (`ocr.py`'s `read()` dispatch checks `anpr_ocr` first, then `easyocr`, then `crnn`, then classical) — `sim/`, `api/`, `dashboard/` construction is untouched, so this never affects the live/default path. `anpr/compare_backends.py` benchmarks all four backends together: `--real` (pre-cropped real plates) and `--real-frames` (whole real photographs through `detect_plate_candidates()`, i.e. the YOLOv8-OBB detector) both iterate every backend that's installed.

`anpr_ocr` wraps `Awiros/anpr-ocr` (Hugging Face, Apache-2.0, PP-OCRv5/PPHGNetV2_B4, pretrained on 558k real Indian plates) — real-photo accuracy far ahead of the others. **91.0% per-frame exact-match over the whole 532-crop real corpus, 93.8% mean / 86.8% min / 97.1% max over an 8-seed vehicle split** (vs EasyOCR ~13%, classical ~4%, CRNN ~2%). Getting there took two independent fixes — the ground truth was wrong, and the recogniser was under-driven — both described below. It needs `paddlepaddle`, which **has no Python 3.14 wheels** — this repo's main `.venv` can't run it, so a separate `.venv-paddle` (Homebrew Python 3.12, full dependency stack reinstalled) is what anything touching `anpr_ocr` must run under. `_ensure_paddleocr()` auto-clones `PaddlePaddle/PaddleOCR` into `models/anpr_ocr/PaddleOCR/` on first use (needed for the `ppocr` package — not on PyPI standalone), and `_ensure_weights()` downloads `model.safetensors`/`en_dict.txt` from the HF repo into `models/anpr_ocr/`, all cached, none of it committed.

**Load-order hazard, real and reproducible**: in `.venv-paddle`, importing `paddle` and then *later* triggering a torch model load in the same process (e.g. `anpr.ocr._load_yolo()`, or `anpr.crnn.load()`) corrupts torch's tensors with a paddle C++ error (`PreconditionNotMet - Tensor holds no memory`) — a binary symbol clash between the two frameworks' compiled extensions. `anpr_ocr_reader.load()` defends against this itself (loads YOLO + CRNN first, before touching paddle), but any other code path that imports `paddle` before torch's models are loaded will hit it.

**Fine-tuning `anpr_ocr` on the same 439-crop real train set did not help** (`build_anpr_ocr_finetune_data.py` builds the PaddleOCR `SimpleDataSet` label files; `models/anpr_ocr/finetune_config.yml` + `PaddleOCR/tools/train.py` run the fine-tune, needs `pip install -r PaddleOCR/requirements.txt` for training-only deps beyond what inference needs — `albumentations`, `lmdb`, `rapidfuzz`). Val accuracy plateaued at epoch 4 (~49.5%) and never improved through epoch 15 while train loss kept falling — classic overfitting on too little real data, same conclusion as the CRNN fine-tune above, just for a stronger starting checkpoint. `anpr_ocr_reader.load(checkpoint_path=...)` can load a fine-tuned `.pdparams` checkpoint instead of the HF base weights, for exactly this kind of before/after comparison.

**`indian-number-plates-dataset/` is already complete — do not try to re-download it for more images.** Its dataset card (Dataclusterlabspvtltd/indian-number-plates-dataset on HF, CC BY-NC-ND 4.0) advertises a "~200 image" free sample against a 15,000+ commercial set, which reads like a 4x expansion is sitting there for free. It is not: `list_repo_files` returns 96 files — 47 images, 47 Pascal-VOC XMLs, README, .gitattributes — exactly what is already checked out, 52 boxes of which 25 carry `number_plate_text`. The card's number is wrong. More real labelled Indian plates have to come from somewhere else (Kaggle `saisirishan/indian-vehicle-dataset` and `kedarsai/indian-license-plates-with-labels` are unverified candidates; `sanchit2843/Indian_LPR` is 16k images with character-level labels but is not public; the DataCluster full set needs a commercial licence).

**Per-frame ground truth for the dashcam frames lives in `real_plate_frame_labels.json` — see `REAL_LABELS.md`.** The 548 video frames used to be labelled by propagating one hand-typed plate across each cluster of adjacent frames (`cluster_manifest.json` + `real_plate_transcriptions.json`). Adjacency is not vehicle identity: cluster 6 held six different vehicles under `MH47Y1124`, cluster 39 held eight, cluster 43 was thirteen frames of `MH03CS6266` and one of its namesake — **37% of frames carried a plate that is not in the picture**, capping accuracy far below what the reader was achieving. The two old files are kept for provenance only; `build_real_crnn_dataset.frame_labels()` is the ground truth, and both `_load_real_dataset()` and `_load_real_frames_dataset()` read it. Re-labelling alone moved the *unchanged* upstream decoder from 48.7% to 79.5%. Don't reintroduce cluster-propagated labels, and don't relabel from model output without looking at the image.

**`anpr/anpr_ocr_reader.py` does its own decoding — do not replace it with ppocr's `CTCLabelDecode`.** ppocr's decode is a plain argmax with no notion of a registration; that is what emitted `MH02ER9194JH` (state sticker read as characters) and `MH02AQ229` (dropped digit). The reader instead folds the 64 output classes onto the 36 plate characters, runs a CTC prefix beam search, proposes every legal reading each beam admits (`_grammatical_readings()`), and ranks them by the exact CTC score of the whole string — reusing `crnn.ctc_score()`, which now takes `idx`/`blank`/`is_probs` for exactly this and is still verified against `torch.nn.CTCLoss` (2.8e-14). Grammar is safe here: 76/76 ground-truth labels carry a real state code and 74/76 match `PATTERNS`. An ungrammatical read is still returned when nothing legal is on the beam, so an unusual format degrades rather than disappearing. `matches_plate_grammar()` / `plate_shape()` / `repair_state_code()` are module-level in `anpr/ocr.py` so both the engine and this backend share one grammar.

**Two-row plates need `_split_rows()`.** Every dual-row plate in the corpus was misread — `MH04DW9020` → `MH04DWM020`, `MH01BU1852` → `MH01BU852`, `MH47AV6753` → `MH47AV753`, `MH02EZ2599` → `MH022599` — while single-row plates were near-perfect. It is geometric, not semantic: `_resize_for_rec()` preserves aspect at a fixed 48px height, so a square plate lands 48x48 in a 320-wide canvas at ~20px per character row. `read()` cuts at the gutter, lays the rows side by side, decodes that too, and keeps the better read. It is an additional candidate, never a replacement. `_prefer()` ranks legality above confidence when choosing — a legal plate at 0.64 beats an illegal string at 0.99, which is what stopped `MH47AV753` from outscoring the correct `MH47AV6753`.

**`--real-all` is the mode for comparing two decoders**; `--real --seeds 8` answers the held-out question. No backend is trained in this repo, so for a zero-shot recogniser the vehicle split only adds noise — scoring every crop once, with a per-source breakdown, is the stable comparison.

**Measurement instability — a single seed on this dataset is not a stable number.** `compare_backends.py`'s `--real`/`--real-frames` vehicle-split seed is **independent from** `--seed` (which is synthetic-mode only, default 4242) — use `--real-seed`/`--seeds N` for the real modes; these two defaults used to be silently conflated (the CLI passed `--seed`'s value into the real-data split), which is how a 19-point swing in `anpr_ocr`'s reported accuracy went unnoticed for a while. With ~118 unique vehicles, *which* ones land in val still moves the result more than a small code change does — though far less than it did under the old labels, where an 8-seed sweep of the identical model swung `anpr_ocr` from 35% to 81% (spread 46 points; it is 10 points now). `_vehicle_split()` is the one shared split implementation (`run_real()`/`run_real_frames()` had each reimplemented it separately before — don't reintroduce that); `run_real_multiseed()`/`run_real_frames_multiseed()` report mean/min/max across seeds instead of one arbitrary number, which is the only honest way to quote this dataset's accuracy until it's meaningfully larger.

`detect_plate_candidates()`'s YOLOv8-OBB path collapses each detection's 4-point rotated polygon to an axis-aligned box, discarding rotation/skew. `_obb_rectified_crop()` (`ocr.py`, via the `_last_obb_polygons` side-channel keyed by box tuple) adds a perspective-rectified crop as one more candidate in `_crop_variants()` — additive, every other backend's behaviour is unchanged. Measured effect on the current real-photo set: none — this dataset's YOLO detections are already within ~0.2% of axis-aligned (median), so the fix has almost nothing to correct. Real for genuinely oblique captures; don't expect it to move this dataset's numbers.
